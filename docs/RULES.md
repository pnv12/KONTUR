# Правила разработки KONTUR

## 1. Общие принципы

1. Приоритеты разработки: корректность, безопасность, проверяемость и простота сопровождения.
2. Не добавлять возможности только ради увеличения количества кода.
3. Не выдавать запланированную функциональность за реализованную.
4. Не утверждать, что код проверен, если соответствующая проверка фактически не выполнялась.
5. Не скрывать известные ошибки, ограничения и незавершённую работу.
6. Каждое изменение должно соответствовать текущему этапу дорожной карты.

## 2. Размер и организация файлов

1. Целевой размер одного исходного файла — не более 300 строк.
2. Если файл приближается к этому пределу, оценить возможность разделения по ответственности.
3. Не дробить код искусственно, если это усложняет архитектуру.
4. Каждый модуль должен иметь чёткую ответственность.
5. Не дублировать существующую логику, типы, константы и проверки.
6. Перед добавлением нового модуля проверить, не существует ли уже подходящей реализации.
7. Не создавать второй источник истины для одного и того же состояния или набора данных.
8. Не смешивать симуляцию, отрисовку, интерфейс, хранение данных и интеграцию приложения в одном модуле.

## 3. API и зависимости

1. Не выдумывать API библиотек, методы, свойства, параметры или типы.
2. Использовать API, подтверждённый документацией именно установленной версии зависимости.
3. Не переносить примеры из другой версии библиотеки без проверки совместимости.
4. Не использовать устаревшие методы, если для установленной версии предусмотрен другой API.
5. Не добавлять зависимость без конкретной необходимости.
6. Версии зависимостей должны быть зафиксированы без диапазонов `^` и `~`.
7. Не создавать циклические импорты.
8. Соблюдать направления зависимостей, определённые в `ARCHITECTURE.md`.
9. Логика `src/sim/` не должна зависеть от DOM, PixiJS, браузерного хранилища или файловой системы.

## 4. Полнота реализации

1. Не оставлять заглушки вместо требуемой реализации.
2. Не использовать фиктивные данные, фиктивные результаты или имитацию успешной работы вместо реальной логики.
3. Не оставлять пустые обработчики, фиктивные возвращаемые значения или необработанные TODO там, где требуется работающий функционал.
4. Если реализация невозможна на текущем этапе, явно указать причину и согласовать изменение объёма работы.
5. Не добавлять функции, которые заявлены как работающие, но фактически не реализованы.
6. Не маскировать ошибки пустыми блоками `catch` или безусловным продолжением работы.
7. Ошибки должны обрабатываться явно и предсказуемо.
8. Не удалять проверки ради прохождения тестов.

## 5. Данные и конфигурация

1. Игровые наборы данных хранить в JSON, а не дублировать в коде.
2. Алгоритмы должны обрабатывать данные, а не содержать параллельные копии этих данных.
3. Проверять внешние данные до их использования.
4. Для игровых данных и сохранений определять допустимую структуру и значения.
5. Не обходить валидацию при загрузке данных или сохранений.
6. Не хранить секреты, пароли, токены, приватные ключи и другие учётные данные в репозитории.
7. Не вставлять реальные секреты в тесты, документацию, примеры или конфигурационные файлы.
8. Не менять настройки безопасности без конкретного обоснования и проверки совместимости.

## 6. Симуляция и детерминизм

1. Симуляция работает с фиксированным шагом времени.
2. Результат не должен зависеть от частоты кадров или скорости отрисовки.
3. Для случайных событий использовать генератор с явным начальным seed.
4. Не использовать `Math.random()` в логике симуляции.
5. При одинаковом начальном состоянии, seed и последовательности команд результаты должны воспроизводиться.
6. Отрисовка и интерфейс не должны напрямую изменять состояние симуляции.
7. Изменения состояния должны проходить через определённые интерфейсы симуляции.

## 7. Тесты и проверки

1. Новую логику сопровождать соответствующими автоматическими тестами.
2. Проверять не только успешные сценарии, но и некорректные входные данные и ошибки.
3. Тесты симуляции не должны требовать запуска графического движка или DOM.
4. Перед завершением этапа запускать доступные проверки: линтер, проверку типов, тесты и сборку.
5. Если проверка не запускалась, прямо указать это в отчёте.
6. Не сообщать об успешной сборке или прохождении тестов без подтверждённого результата.
7. Не исправлять тест изменением ожидаемого результата без проверки правильности поведения.
8. Не считать успешную сборку доказательством корректности всей игровой логики.

## 8. Работа ИИ-кодера и изменения репозитория

1. ИИ-кодер не получает права записи в репозиторий.
2. Все изменения вносит человек вручную через интерфейс GitHub или другой выбранный человеком инструмент.
3. ИИ-кодер подготавливает полное содержимое файлов и точные пути.
4. Не требовать от пользователя ручного поиска и исправления отдельных строк, если можно предоставить полный файл.
5. Не заменять часть файла фрагментом с указанием оставить остальное без изменений.
6. Не заявлять, что файл создан, изменён или закоммичен, пока человек не выполнил действие и результат не подтверждён.
7. Не выдавать подготовленный код за код, уже находящийся в репозитории.
8. Не выполнять действия записи в репозиторий от имени ИИ-кодера.

## 9. Формат выдачи кода

1. Указывать точный путь каждого файла.
2. Предоставлять полное содержимое каждого изменяемого файла.
3. Не превышать лимит в три файла за один ответ.
4. Не смешивать содержимое нескольких файлов в одном блоке кода.
5. Не сокращать код многоточиями и не заменять части поясняющими комментариями.
6. Для новых файлов указывать путь, который можно сразу ввести в поле имени файла GitHub.
7. Сохранять совместимость с уже согласованными файлами и конфигурацией проекта.

## 10. Отчёт по каждому этапу

В конце каждого этапа предоставить отчёт, содержащий:

1. Какие файлы требовалось создать или изменить.
2. Какие изменения подготовлены и для чего они нужны.
3. Какие действия пользователь должен выполнить в GitHub.
4. Что открыть после коммита и что должно быть видно.
5. Какие проверки фактически выполнены и каков их результат.
6. Какие проверки не выполнялись.
7. Какие известные проблемы, ограничения или зависимости остаются.

Не объявлять этап завершённым только на основании того, что код подготовлен. Учитывать факт добавления файлов и результаты необходимых проверок.
