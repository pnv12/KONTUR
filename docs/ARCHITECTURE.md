# Архитектура KONTUR

## 1. Назначение

Архитектура разделяет игровую симуляцию, отрисовку, интерфейс, данные и сохранение. Цель — сделать логику проверяемой, детерминированной и независимой от графического движка.

Документ описывает целевую архитектуру этапа 0. Наличие описанного компонента не означает, что он уже реализован.

## 2. Слои проекта

### 2.1. `src/sim/` — симуляция

Содержит игровое состояние и правила его изменения.

Ответственность:
- хранение состояния симуляции в определённых типах данных;
- выполнение одного шага симуляции;
- использование воспроизводимого генератора случайных чисел;
- соблюдение фиксированного шага времени;
- предоставление состояния для чтения другими слоями.

Ограничения:
- не импортировать PixiJS;
- не обращаться к DOM и браузерному интерфейсу;
- не читать и не записывать файлы;
- не обращаться к `localStorage`;
- не зависеть от `render`, `ui`, `data` или `persistence`.

Симуляция не должна зависеть от частоты кадров и времени выполнения отрисовки.

### 2.2. `src/render/` — отрисовка

Преобразует состояние симуляции в графическое представление с помощью PixiJS.

Ответственность:
- отрисовка карты и игровых объектов;
- управление камерой и масштабированием;
- обновление визуального представления;
- наблюдение за производительностью отрисовки.

Ограничения:
- читать состояние симуляции, но не изменять его;
- не реализовывать игровые правила;
- не определять результаты игровых действий;
- не хранить собственную альтернативную версию игрового состояния.

### 2.3. `src/ui/` — интерфейс

Отвечает за элементы управления и отображение информации игроку.

Ответственность:
- отображение игровых показателей;
- обработка пользовательского ввода;
- настройка доступных параметров интерфейса;
- передача намерений пользователя интеграционному слою приложения.

Ограничения:
- не изменять состояние симуляции напрямую;
- не дублировать игровые правила;
- не считать отображаемые данные источником истины.

Изменение игрового состояния должно проходить через предусмотренный API приложения и симуляции.

### 2.4. `src/data/` — игровые данные

Содержит данные, отделённые от алгоритмов.

Ответственность:
- хранение игровых описаний в JSON;
- предоставление схем и правил валидации;
- проверка структуры, типов и допустимых значений данных;
- загрузка только проверенных наборов данных.

**Принцип: данные хранятся в JSON, а не зашиваются в игровой код.** Алгоритмы определяют, как обрабатывать данные; JSON определяет значения и описания игровых объектов.

Исключения допустимы только для технических констант, параметров алгоритмов и других значений, которые по назначению не являются игровыми наборами данных.

### 2.5. `src/persistence/` — сохранение

Отвечает за сохранение, загрузку, импорт и экспорт состояния.

Ответственность:
- определение формата сохранения;
- проверка версии и структуры сохранения;
- валидация данных до их применения;
- обработка ошибок хранения, чтения и разбора;
- взаимодействие с выбранным хранилищем.

Ограничения:
- не реализовывать игровые правила;
- не обходить валидацию при загрузке;
- не передавать непроверенные данные напрямую в симуляцию.

Симуляция не должна импортировать persistence. Это позволяет тестировать её без браузерного хранилища.

### 2.6. `src/app/` — интеграция

Создаёт и связывает компоненты приложения.

Ответственность:
- инициализация симуляции;
- создание отрисовки и интерфейса;
- организация игрового цикла;
- передача состояния для чтения в `render` и `ui`;
- координация пользовательских команд и изменения состояния.

Интеграционный слой связывает компоненты, но не должен превращаться в место для всех игровых правил.

## 3. Направление зависимостей

Базовые ограничения:

- `sim` не зависит от других слоёв проекта.
- `render` читает состояние `sim`, но не изменяет его.
- `ui` читает состояние `sim` и передаёт команды через предусмотренный интерфейс приложения.
- `data` предоставляет данные и механизмы их проверки.
- `persistence` отвечает за хранение и валидацию сохранений, но не определяет игровые правила.
- `app` связывает компоненты и управляет их жизненным циклом.

Запрещены циклические зависимости и обратные импорты из симуляции в интерфейсные, графические или инфраструктурные модули.

## 4. Фиксированный шаг симуляции

Симуляция выполняется с фиксированным шагом времени — 60 тиков в секунду.

Один тик представляет собой один определённый шаг изменения игрового состояния. Отрисовка может выполняться с другой частотой, но не должна менять длительность игрового тика.

Если отрисовка задерживается, игровой цикл может выполнять несколько тиков подряд, однако количество догоняющих шагов за один кадр должно быть ограничено. Это предотвращает бесконтрольную нагрузку при длительных задержках.

Нельзя подменять фиксированный шаг симуляции произвольным временем между кадрами.

## 5. Детерминизм

При одинаковом начальном состоянии, одинаковой последовательности команд и одинаковом состоянии генератора случайных чисел симуляция должна выдавать одинаковую последовательность состояний.

Для этого необходимо:
- использовать генератор случайных чисел с явным начальным seed;
- не полагаться на `Math.random()` в логике симуляции;
- не зависеть от времени системы и частоты кадров;
- поддерживать определённый порядок обработки игровых объектов;
- избегать недетерминированного порядка обхода данных;
- проверять воспроизводимость автоматическими тестами.

Хеш состояния может использоваться в тестах для сравнения результатов. Он не является криптографической гарантией целостности или безопасности.

## 6. Тестирование

Тесты симуляции должны запускаться без PixiJS и DOM.

Минимальные требования:
- повторное выполнение с одинаковым seed даёт одинаковый результат;
- изменение seed может изменять результаты там, где используется случайность;
- валидация отклоняет некорректные игровые данные;
- валидация сохранений отклоняет данные неподходящей структуры;
- ошибки внешних данных обрабатываются явно.

Успешная сборка сама по себе не доказывает корректность игровой логики.

## 7. Безопасность и обработка ошибок

Все внешние данные считаются недоверенными, включая импортируемые JSON и сохранения.

Необходимо проверять структуру, типы, допустимые диапазоны и ограничения размера до использования данных. Ошибки загрузки и сохранения не должны приводить к молчаливому повреждению состояния.

Секреты, токены и приватные ключи не должны попадать в исходный код, конфигурацию репозитория или тестовые данные.

## 8. Критерии архитектурного изменения

Перед добавлением нового модуля необходимо определить:
- его ответственность;
- допустимые зависимости;
- формат входных и выходных данных;
- способ тестирования;
- обработку ошибок.

Нельзя создавать второй источник истины для игрового состояния, дублировать уже существующую реализацию или вводить API, не подтверждённый установленной версией зависимости.
